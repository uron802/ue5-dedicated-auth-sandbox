# 部屋機能 設計方針

状態: **設計のみ。実装・検証はまだ行っていない。**
既存の認証基盤は [AccountAuthentication.md](AccountAuthentication.md) を参照。

## 目的

認証済みのプレイヤーが部屋を作り、複数人で入室できるようにする。
例: 4人のうち2人が部屋A、残り2人が部屋Bに入り、部屋ごとに独立して遊ぶ。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 方式 | 部屋ごとに Dedicated Server のプロセスを1つ立てる（B案） | 部屋ごとにワールドが分かれるため、他の部屋の非表示・衝突回避・状態の分離を自前で作る必要がない |
| PlayFab クラウド | Lobby / Multiplayer Servers は今回使わない | 費用と検証環境の都合。役割は自前で実装する |
| PlayFab 認証 | 既存の実装を引き続き使う | Lobby / Multiplayer Servers とは別の基本機能 |
| 定員 | 全部屋で共通の固定値 4人 | 部屋ごとの指定はしない |
| 部屋の数の上限 | 同時に4部屋まで | |
| 部屋の作成 | 認証済みなら誰でも作れる。作成者は自動で入室し、ホストになる | |
| 開始の段階 | 設ける。「待機中」から、ホストの操作で「プレイ中」に移る | |
| パスワード付きの部屋 | 対応する。8〜64文字、印字可能な ASCII 文字と空白 | NIST SP 800-63B の記憶型シークレットの規定に準じる（下記） |
| 空になった部屋の停止 | 全員が退室してから60秒後に部屋サーバーを停止する | 切断直後の再接続に猶予を残すため |
| 部屋サーバーの異常終了 | ロビーが検知して部屋を一覧から消し、メンバーをロビーへ戻す。自動での再作成はしない | 下記「異常時の扱い」 |
| 部屋管理の作り方 | 窓口をインターフェースにし、今回はローカル版だけを実装する | 窓口の形を Lobby に揃えておけば、後で PlayFab 版に差し替えられる |
| 認証のローカル検証 | PlayFab の認証 API を偽のサーバーで再現する | 本番と同じ認証コードを別プロセスで動かしたまま、自動で検証できる |

### 検討して採らなかった案

- **A案（1つのサーバー内に論理的な部屋を作る）**: UE は1プロセス1ワールドのため、部屋が同じマップを共有する。
  他の部屋のアクタを送らない処理、部屋ごとの配置の分離、状態の分離が必要になり、B案へ移ると捨てる作業になる。
- **PlayFab Lobby / Multiplayer Servers**: 下記「PlayFab クラウドについての調査メモ」を参照。

## 構成

```
クライアント ──(1) ログイン・部屋一覧・作成・入室──▶ ロビーサーバー
     │                                              │ (2) 部屋が作られたら、空いているポートで
     │                                              │     部屋サーバーのプロセスを起動する
     │                                              ▼
     └──(3) 参加券を持って接続──────────────▶ 部屋サーバー（部屋A: 7778、部屋B: 7779 …）
```

### ロビーサーバー

- 既存の Dedicated Server（`AAccountGameMode` の認証ゲート）をロビーとして使う。
- 部屋の一覧・作成・入室・退室を受け付ける。部屋の情報はロビーサーバーのメモリで管理する（再起動で消える）。
- クライアントとのやり取りは、既存の DTLS 暗号化済みのゲーム接続の上で行う。
- 部屋の作成時に部屋サーバーのプロセスを起動し、全員が退室したら停止する。
  Multiplayer Servers の代わりになる部分。
- 同時に存在できる部屋は4つまで。上限に達しているときの作成要求は拒否し、クライアントにその旨を返す。

### 部屋サーバー

- ロビーサーバーが起動する別プロセスの Dedicated Server。部屋ごとに1つ。
- 接続してきたプレイヤーを次の2つで照合し、両方が通った場合だけ受け入れて Pawn を生成する。
  1. 既存の PlayFab 認証（`Server/AuthenticateSessionTicket`）でプレイヤーIDを得る
  2. ロビーが発行した参加券が、この部屋とそのプレイヤーIDに対して有効か
- 参加券だけで受け入れないのは、参加券が漏れた場合に他人が使えないようにするため。
- DTLS 暗号化を有効にする。同じPC上では証明書ファイル（`GAMEAUTH_DTLS_CERTIFICATE_FILE`）を共有できる。

### 参加券

- ロビーが「このプレイヤーIDは、この部屋に入ってよい」と保証する券。
- 含める情報: 部屋ID、プレイヤーID、有効期限（短時間）、一度だけ使うための識別子。
- ロビーが署名し、部屋サーバーが検証する。署名鍵はロビーの起動ごとに生成し、部屋サーバーを起動するときに子プロセスへ渡す。
  ファイルやログには残さない。
- 送り先はクライアント、提出先は部屋サーバーで、どちらも暗号化済みの接続を使う。URL のオプションには載せない。
- 部屋サーバーは、期限切れ・他の部屋の券・他人の券・使用済みの券を拒否する。

### 定員

- 全部屋で共通の固定値で、**4人**。値はプロジェクト設定に置く。
- 判定はロビーが行う。満員の部屋には参加券を発行しない。
- 部屋サーバー側でも、定員を超える接続を拒否する（ロビーの判定と部屋サーバーへの接続の間に起きる競合への備え）。
- 定員には作成者（ホスト）も含む。

### 部屋の状態と流れ

```
作成 ──▶ 起動中 ──▶ 待機中 ──(ホストが開始)──▶ プレイ中 ──(全員退室 + 60秒)──▶ 停止
            │           │                          │
            └─ 起動失敗 ─┴──── 部屋サーバーの異常終了 ──┴──▶ 停止（メンバーはロビーへ戻る）
```

| 状態 | 内容 | 新しい入室 | 一覧での表示 |
|---|---|---|---|
| 起動中 | 部屋サーバーのプロセスが立ち上がるのを待つ | 不可 | 表示しない |
| 待機中 | メンバーが集まるのを待つ。部屋サーバーに接続し、メンバー一覧を見ながら待つ。Pawn は生成しない | 可（定員まで） | 表示する |
| プレイ中 | 遊んでいる最中。開始時に全員の Pawn を生成する | 不可 | 「プレイ中」として表示し、入室はできない |
| 停止 | 部屋サーバーのプロセスを止め、一覧から消す | 不可 | 表示しない |

- **作成**: 作成者は部屋の作成と同時に参加券を受け取り、部屋サーバーが待機中になったら自動で接続する。作成者がホストになる。
- **開始**: 開始の操作ができるのはホストだけ。待機中の部屋に1人以上いれば開始できる（1人での動作確認を妨げないため）。
- **ホストの退室**: 待機中・プレイ中にホストが退室した場合、残っているメンバーのうち最も早く入室した人がホストを引き継ぐ。
- **プレイ中の退室**: 退室した人の Pawn は破棄する。プレイ中の部屋に後から入る・戻ることはできない。
- **空になった部屋**: 全員が退室してから60秒後に部屋サーバーを停止する。60秒以内に入室があれば停止しない（待機中の部屋のみ。プレイ中の部屋には入れないため、プレイ中に全員が抜けた部屋は60秒後に停止する）。
  作成者が部屋サーバーに一度も接続しなかった場合も、同じく60秒後に停止する。

### パスワード付きの部屋

- 作成時にパスワードを設定できる。部屋の一覧には「パスワード付き」であることだけを表示し、パスワードそのものは送らない。
- **規定**: NIST SP 800-63B（記憶型シークレット）に準じる。
  - 長さは8文字以上64文字以下。
  - 文字の種類の組み合わせ（大文字・数字・記号を必ず含む、など）は要求しない。
  - 使える文字は印字可能な ASCII 文字（`0x20`〜`0x7E`、空白を含む）。
    NIST は Unicode も受け付けることを推奨しているが、入力方式（IME）や正規化による不一致を避けるため、今回は ASCII に限る。
  - 前後の空白は削らず、入力どおりに扱う。
- ロビーはパスワードを平文で保持せず、ソルト付きの鍵導出関数（PBKDF2 など）でハッシュ化して保持する。
- 照合はロビーが行い、一致した場合だけ参加券を発行する。部屋サーバーにはパスワードを渡さない。
- 同じプレイヤーが同じ部屋で5回続けて失敗したら、60秒間その部屋への入室を受け付けない。
- 失敗時のメッセージは「パスワードが違います」に統一し、部屋の存在以外の情報を返さない。
- パスワードはログ・検証結果に出力しない。

### 異常時の扱い

- **部屋サーバーの異常終了**: ロビーは起動した部屋サーバーのプロセスを1秒ごとに確認し、予期せず終了したら次を行う。
  1. 部屋を一覧から消す。
  2. 部屋サーバーとの接続が切れたメンバーのクライアントは、ロビーへ接続し直し、「部屋が終了しました」と表示する。
  3. 終了コードとログの場所をロビーのログに記録する。
  4. 部屋を自動では作り直さない。
- **部屋サーバーの起動失敗**: 起動から30秒以内に待機中にならなければ起動失敗とする。プロセスを止め、作成者に失敗を伝える。
- **ロビーサーバーの終了**: 部屋サーバーは親のロビーサーバーのプロセスを監視し、ロビーが終了したら自分も終了する（取り残されたプロセスを残さないため）。
  ロビーの再起動で部屋の情報は失われる。
- **応答しなくなった部屋サーバー（ハング）**: プロセスの生存確認だけでは検知できない。今回は対象外。

### 部屋管理の窓口

- 「部屋一覧・作成・入室・退室」と「部屋サーバーの確保」を、それぞれインターフェースとして定義する。
- 今回の実装はローカル版（上記のロビーサーバーと部屋サーバーの起動）だけ。
- 窓口は最初から「応答は後から返る」「失敗することがある」前提の形にする。
  ローカル版でも遅延と失敗をわざと起こせるようにし、その経路をテストする。
  PlayFab 版に差し替えたときに、通信の遅延や失敗で初めて不具合が出ることを防ぐ。

## ローカルでの検証方法

### 起動方法

このPCのエンジンはインストール版（`Engine/Build/InstalledBuild.txt` あり）のため、Server ターゲットのビルドは作れない。
エディタの実行ファイルを別プロセスで起動して検証する。

- サーバー: `UnrealEditor-Cmd.exe <project> DemoMap -server -port=<ポート>`
- クライアント: `UnrealEditor.exe <project> 127.0.0.1:<ポート> -game`

1プロセスあたりのメモリ使用量が大きい。上限いっぱいの構成はサーバー5つ（ロビー1・部屋4）と、各部屋にクライアントがいればその数だけ増える。
このPCで同時に動くかは未測定。最初に、ロビー1・部屋2・クライアント4の構成でメモリ使用量を測る。

### 認証のモック

クライアントとサーバーが呼ぶ PlayFab の認証 API を、同じ URL の形・同じ JSON で応答する偽のサーバーで再現する。

| 呼び出し元 | API |
|---|---|
| クライアント | `Client/LoginWithEmailAddress`、`Client/RegisterPlayFabUser` |
| サーバー | `Server/AuthenticateSessionTicket` |

- 接続先だけを `localhost` に切り替える。偽のサーバーは別プロセス間のチケット共有も担う。
- テストユーザーは偽のサーバー上の架空のもの。外部に何も送らず、PlayFab のアカウント作成枠（開発モードで累計1,000件）も消費しない。
- **安全上の必須条件**
  - 接続先の切り替えは開発ビルドだけで有効にし、`localhost` 以外を許可しない。
    本番で切り替えられると、本物のチケットを第三者のサーバーへ送らせることができてしまう。
  - モック使用時は、本物の `PLAYFAB_TITLE_SECRET_KEY` を送らない。ダミーの値を使う。
- 既存のエディタ内の仮認証（PIE専用）は今のまま残す。

### 自動検証の内容（予定）

クライアントには「起動後に自動でログインし、指定の部屋を作成または入室して、結果をログに出す」検証モードを持たせる。
MCP はエディタにしか接続できず、別プロセスのゲーム画面は操作できないため、判定はログで行う。

- 4人のうち2人が部屋A、2人が部屋Bに入り、各部屋サーバーにその2人だけが接続している
- 定員を超える入室を拒否する（4人が入った部屋に5人目が入れない。クライアントが5つ必要）
- パスワード付きの部屋: 正しいパスワードで入室でき、誤ったパスワード・パスワードなしでは入室できない。連続失敗が制限される
- 参加券: 期限切れ・他の部屋の券・他人の券・使用済みの券を部屋サーバーが拒否する
- 参加券なしで部屋サーバーへ直接接続しても Pawn が生成されない
- 部屋の数の上限: 4部屋ある状態で5つ目の作成を拒否する
- 作成者が自動で入室し、ホストになる
- 開始: ホスト以外は開始できない。開始前は Pawn がなく、開始後に全員の Pawn が生成される。プレイ中の部屋には入室できない
- ホストが退室すると、最も早く入室したメンバーがホストを引き継ぐ
- パスワードの規定: 7文字以下・65文字以上・ASCII 以外の文字を含むパスワードでは部屋を作れない
- 全員が退室してから60秒後に部屋サーバーのプロセスが停止し、60秒以内の入室では停止しない
- 部屋サーバーのプロセスを強制終了すると、部屋が一覧から消え、メンバーがロビーへ戻る
- 部屋サーバーが30秒以内に待機中にならないと、起動失敗として作成者に伝わる
- ロビーサーバーを終了すると、部屋サーバーのプロセスも終了する
- 部屋サーバーへの接続で DTLS ハンドシェイクが完了している
- ロビーの応答遅延・失敗を起こしたときに、クライアントがエラーとして扱う

### 自動検証できないこと

- **実 PlayFab での認証**: 外部サービスへのパスワードを使ったログインは Claude が実行しない。
  節目ごとに、テストユーザーでのログインから結果の書き出しまでを1つのコマンドにまとめ、ユーザーが実行する。
  結果のファイルとログを Claude が読んで判定する。
  - 2人ずつ2部屋の検証には、テストユーザーが4件必要（現在は2件）。同じIDの同時接続は拒否されるため、1件で兼ねられない。
  - 毎回アカウントを作らず、決まったテストユーザーでログインする（開発モードの累計1,000件の枠を消費しないため）。
- **画面の見た目とキー操作**: 従来どおりユーザーが確認する。
- **パッケージ版の Dedicated Server**: ソースからビルドしたエンジンが必要。今回の範囲外。

## PlayFab クラウドについての調査メモ（2026-10-15〜20）

今回は採用しない。将来採用する場合の前提として残す。料金は変わるため、採用時に公式ページで再確認すること。

- **役割の違い**: Lobby は部屋の名簿（作成・一覧・入退室・メンバー管理）で、ゲームは動かさない。
  Multiplayer Servers はアップロードしたサーバーを Azure で起動・割り当てるもので、部屋や名簿の概念は持たない。
- **Lobby の料金**: Lobby API のエンドポイントを1回呼ぶごとに LobbyRequests が1件（100万件あたり $9.90）。
  リアルタイム通知は受信者1人ごとに Messages が1件（100万件あたり $1）。
  開発モードで無料になるか、最低請求額があるかは未確認。
- **Multiplayer Servers の料金**: 毎月 750 コア時間（米国東部と北ヨーロッパのみ）と、ゾーンごとに通信量 10GB が無料。
  超過分は従量課金。2026-11-01 から VM 料金が平均約6%値上げと告知されている。
  待機サーバーは使われていなくても時間を消費する。日本のリージョンは無料枠の対象外。
- **開発モード**: 1タイトルあたりアカウント作成は累計1,000件まで。
- **ローカルでのテスト**: Multiplayer Servers は公式の LocalMultiplayerAgent でローカル実行できるが、パッケージしたサーバービルドが前提。
  Lobby をオフラインで再現する公式の手段は見つからなかった。
- **採用時の前提**: Multiplayer Servers へはパッケージしたサーバービルドをアップロードするため、ソースからビルドしたエンジンが必要。
